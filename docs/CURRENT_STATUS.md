## Дефект задвоения позиций и его закрытие

Дедуп позиций смотрел только на «ID импорта», а он считается из sha файла, листа
и номера строки, то есть уникален для каждой строки Один товар одного заказа мог
занять две позиции Количество не терялось, но склад видел две одинаковые строки,
а SkladBot одну суммарную

Дополнительно поле «ID заказа» из Excel не было идентификатором заказа: в хеш
входили `product` и `row` На боевом импорте 70 строк давали 70 разных
«ID заказа» при 24 реальных заказах

Решение и разбор: [склейка позиций заказа](order-position-merge-2026-07-31.md)

Починка данных 2026-07-31: 7 групп в 5 заказах, 22 блока до и после, удалено 7
поглощённых позиций, перенесено 2 скан-кода и 2 движения КИЗ, осиротевших
записей `0` Backup снят до записи

Ограничение доказательства: после выката прошло 39 импортов, все `smartup_auto`,
`merged_position_rows=0` во всех Поле присутствует, то есть новый код исполняется,
но сама склейка на боевых данных ещё не срабатывала Исходный случай пришёл
Telegram-файлом, таких импортов с момента выката не было

## Release-контур

Две правки закрыли дефекты самого выката

**Окно SLO мерило холодный старт** Окно стартовало сразу после пересоздания
backend-контейнера, поэтому первые ответы отражали холодный старт Два прогона
дали p95 `2027 мс` и `502.6 мс` при бюджете `500 мс`, хотя p50 был `172` и
`164 мс` и ошибок не было `collect_live` прогревает три endpoint тремя циклами
до окна и эти пробы в измерение не берёт, прогрев пишется в evidence как
`slo.warmup` Последний деплой: p50 `136 мс`, p95 `438 мс`, `pass`

**Rollback-preflight терял окружение кандидата**
`verify_previous_runtime_preflight` подменяет `RELEASE_*` на прошлый релиз, чтобы
доказать возможность отката, а возвращала назад только 4 переменные из 6, которые
переносит `export_release_runtime_env` От прошлого релиза оставались
`RELEASE_SERVER_RELEASE_ID` и `RELEASE_DESKTOP_API_CONTRACT` Backend уезжал в
production с release id прошлого релиза, из-за чего compose пересоздавал
`backend-api` на каждом деплое даже при идентичном образе В отчётности дефект не
был виден: `health_service` подставляет `server-{commit_sha}`, когда настроенный
id не совпадает с коммитом Окружение кандидата теперь восстанавливается целиком

Проверено после выката: config-hash работающего контейнера и ожидаемого совпадают,
`docker compose up --dry-run` для того же релиза даёт `Running`, а не `Recreate`

## Квиесценция писателей при деплое

Деплой останавливает `backend-api` и три воркера на время cutover-backup и
миграции Измеренное окно записи 2026-07-31: `15.5 с`, из них бэкап `8.9 с`,
миграция `2.6 с`, восстановление лизов `1.6 с`

Оценка выноса квиесценции при `no_change` выполнена 2026-08-01, вывод
отрицательный:

- `MIGRATION_POLICY = "no_change"` это константа `tools/server_release_artifacts.py:26`,
  проверяемая при валидации манифеста и в workflow Другого значения у серверного
  релиза не бывает, поэтому условие всегда истинно и означает снятие защиты целиком;
- `recover_inflight_event_leases_after_worker_stop` (`backend/app/event_leases.py:261`)
  перезапускает все события со `status='processing'` и непустым `lease_owner`
  **без проверки `lease_expires_at`** С живыми воркерами это отберёт лизы у
  событий, которые обрабатываются, и даст дубли `skladbot_request_create` и
  `telegram_notification`

Единственный вариант с приемлемым соотношением, если окно всё же важно: вынести
`pg_dump -Fc` до остановки писателей Дамп берёт консистентный MVCC-снимок и в
квиесценции для консистентности не нуждается, это экономит `8.9 с` из `15.5 с`
Цена решения: точка отката перестаёт быть точкой без незавершённой работы
Отдельного решения владельца нет, изменение не выполнялось

## Открытые пункты

1. **GitHub Actions не используются** Платные функции GitHub сняты решением от
   2026-08-16, а с 2026-08-14 аккаунт и так заблокирован по биллингу: любая
   джоба падает с `The job was not started because your account is locked due
   to a billing issue` Проверено повторным запуском run `32014632098`
   2026-08-17 Следствия, которые нужно держать в голове: нет immutable release,
   нет пакета доказательств, нет sigstore attestation, нет автоматического
   preflight, нет сканов зависимостей Их заменяют локальные прогоны и ручной
   выкат, см. соответствующие разделы
2. **`Release gate` снят из ruleset 2026-08-17** Обязательный статус-чек
   ссылался на джобу Actions и наглухо закрывал `main`: все PR стояли в
   `BLOCKED` Сохранены три правила: `deletion`, `non_fast_forward`,
   `required_linear_history` Если Actions когда-нибудь вернутся, чек нужно
   вернуть, иначе защита ветки останется формальной
3. **Признание заявки по содержимому выключено** Чтобы им пользоваться, нужно
   выставить `SKLADBOT_CONTENT_RECONCILE_ENABLED=1` в боевом `.env` и
   перезапустить воркер Это отдельное решение: механизм привязывает заявку по
   совпадению содержимого, а не по маркеру, и работает только когда список
   заявок заведомо не обрезан лимитом
4. **6 событий `skladbot_daily_report_send` в статусе `failed`**, прочитано в
   боевой базе 2026-08-17 Пять июльских (06.07, 11.07, 12.07, 20.07, 21.07)
   упали на `SKLADBOT_DAILY_REPORT_COVERAGE_NOT_COMPLETE`, у двух из них
   `included=0 excluded=3622` Шестое **новое, от 2026-08-11 17:32**, причина
   другая: `Telegram API request failed: sendDocument: HTTP 504`, то есть
   дневной отчёт за тот день клиенту не ушёл, попытка была одна
   Hot-path не блокируют, `readiness.daily_report` сейчас `ok` с
   `missing_count 0`, разбор ни по одному не проводился
   Прежняя запись «пять штук, новых после 21.07 нет» устарела
5. **18 открытых инцидентов**, прочитано 2026-08-17: 17 от `skladbot_create`
   за 06-08 июля и один `daily_reconciliation` от 07.07, все `critical`
   Августовских нет Отдельно в базе 37 `resolved` (последний 14.08),
   12 `ignored` и 2 `manual_review` от 14.08
6. **Склейка позиций не подтверждена боевыми данными**: нужен Telegram-импорт с

# Разделение отчёта логистики на городской и областной

Дата: 2026-08-04
Статус: согласован с Антоном, к реализации
Согласовано: правило классификации (5 строк), имена файлов и подписи, хранилище справочника

## Задача

Заказы города Ташкента и Ташкентской области развозят разные машины,
но отчёт логистики сейчас один на всех
Нужно разделить его на два отчёта: городской и областной

Источник разделения: адресная программа контрагентов Ташкентской области,
файл `Адресная_программа_контрагенты_Таш_обл_.xlsx`, 400 строк, колонки
`Клиент`, `Широта`, `Долгота`, `Агент`

## Что есть сейчас

- `backend/app/logistics_service.py:110` `build_logistics_report_xlsx(db, shipment_date)`
  собирает один XLSX: лист `Orders` с 31 колонкой плюс лист `Требуют координаты`
- отчёт уходит в чат роли `logistics` (`SMARTUP_AUTO_IMPORT_LOGISTICS_CHAT_ID`):
  автоматически в 17:50 через `smartup_auto_import.py:1943`,
  вручную кнопкой `/logistics` через `telegram_report_processor.py:205`
- имя файла и подпись строит `telegram_output_contract.py:60`
- маршрут и хеш текстов зафиксированы в `telegram_routing_manifest.json`,
  ключ `smartup_logistics_report`, `text_policy_sha256`

## Почему делим по списку, а не по географии

Проверка на данных: из 400 точек «областного» справочника 19 лежат строго внутри
административной границы Ташкента, 32 внутри границы с буфером 1 км
Значит список это зона ответственности агентов, а не география,
и геозона сама по себе дала бы неверный результат

Отсюда: справочник это источник истины, координаты работают только там,
где клиента в справочнике нет

## Правило классификации

Для каждого заказа проверки идут по порядку, первая сработавшая выигрывает:

| # | Условие | Результат |
|---|---------|-----------|
| 1 | клиент найден в справочнике области | областной отчёт |
| 2 | не найден, координаты внутри границы города | городской отчёт |
| 3 | не найден, координаты вне границы города | ни в один отчёт, алерт в админ-чат |
| 4 | не найден, координат нет | городской отчёт, лист `Требуют координаты` |
| 5 | найден в справочнике, координат нет | областной отчёт, лист `Требуют координаты` |

Фильтры, которые действуют до классификации, не меняются:
возвраты, самовывоз и заказы, заблокированные по нехватке остатка,
в логистику не попадают (`is_logistics_candidate_order`)

### Поиск клиента в справочнике

Клиент считается найденным, если сработал любой из трёх уровней:

1. **точное имя**: совпадение нормализованного ключа
   (`normalize_lookup_text`: нижний регистр, `ё` в `е`, всё кроме букв и цифр отброшено)
2. **координаты**: точка заказа в пределах 150 м от любой точки справочника,
   расстояние по формуле гаверсинуса
   Ловит случай «тот же магазин, имя написано иначе»
3. **нечёткое имя**: доля общих значимых токенов не ниже 0.7,
   доля считается от числа токенов в более коротком из двух имён
   Из токенов исключены юридические формы:
   `mchj`, `ytt`, `xk`, `ooo`, `chp`, `sp`, `сп`, `чп`, `ооо`, `мчж`, `ытт`

Только если промахнулись все три, клиент считается незнакомым

Порядок уровней важен: точное имя дешевле координат, координаты надёжнее нечёткого имени

### Алерт по строке 3

Уходит в админ-чат (`TAKSKLAD_AUTOMATION_ALERT_CHAT_ID`) через существующий
kind `admin_error`, отдельный алиас `logistics_zone_unassigned_order`

Содержит по каждому невыясненному заказу:
имя клиента, адрес, координаты, номер складской заявки, товары, дату отгрузки
Этого достаточно, чтобы решить вручную и добавить точку в справочник

Один алерт на дату отгрузки со списком всех невыясненных заказов, не по одному на заказ

## Граница города

Полигон административной границы Ташкента, 13 вершин, плюс буфер 1 км наружу
Точка считается городской, если она внутри полигона
или расстояние до ближайшего ребра не больше 1000 м

Буфер намеренно щедрый: цена ошибки несимметрична
Лишний заказ в городском отчёте это неудобство,
выпавший заказ это несостоявшаяся доставка

Контрольная проверка полигона:

| точка | результат |
|-------|-----------|
| центр Ташкента (Хадра) | город |
| Сергели | город |
| Юнусабад верх | город |
| Чирчик | область |
| Ангрен | область |
| Олмалик | область |
| Зангиата | область |

Полигон приближённый и требует подтверждения на боевых данных
до включения автоматической отправки, см. раздел «Проверка»

## Хранилище справочника

Репозиторий `1fear/TakSklad` публичный, поэтому имена контрагентов и координаты
в git класть нельзя
Справочник живёт в БД, исходный xlsx остаётся локально и попадает в `.gitignore`

Новая таблица `logistics_region_points`:

| колонка | тип | примечание |
|---------|-----|------------|
| `id` | uuid | PK |
| `client_name` | String(255) | как в файле |
| `normalized_client` | String(255) | ключ поиска, индекс |
| `latitude` | Numeric(9,6) | |
| `longitude` | Numeric(9,6) | |
| `agent` | String(64) | `Агент 1`, `Агент 2`, `Агент 3`, nullable |
| `is_active` | Boolean | default true |
| `raw_payload` | JSON | источник, дата загрузки |
| `created_at`, `updated_at` | timestamptz | |

Уникальность по `(normalized_client, latitude, longitude)`
В файле 400 строк и 398 уникальных пар, два полных дубликата
(одинаковое имя и одинаковые координаты) снимаются этим ограничением
естественным образом

Ожидаемый результат загрузки: 398 записей

Имена контрагентов и координаты не попадают ни в этот документ, ни в код,
ни в логи, ни в сообщения об ошибках: репозиторий публичный

## Идемпотентность и ошибки отправки

Текущая семантика сохраняется целиком:
обе отправки идут внутри одного блока обработки одного события

- сборка любого из двух файлов упала: статус `failed`, алерт админу, ничего не отправлено
- городской ушёл, областной упал: статус `ambiguous`,
  `manual_recovery_required: true`, автоматический повтор заблокирован
  Это защита от задвоения: повтор отправил бы городской второй раз
- обе отправки прошли: статус `completed`

Алерт по невыясненным заказам отправляется после обоих документов
и не влияет на статус события: его падение не делает отчёт неуспешным

### Dry-run на боевых данных до включения

Обязательный шаг, без него автоматическая отправка не включается:

1. загрузить справочник скриптом сида с `--dry-run`, сверить числа
2. загрузить справочник, убедиться что записей 398
3. прогнать `tools/logistics_zone_dry_run.py` на 3 прошедших датах отгрузки
4. показать Антону: сколько заказов в городе, сколько в области,
   сколько невыясненных и кто они поимённо
5. невыясненных больше нуля значит справочник или полигон нужно поправить
   до включения, а не после

## Риски

- **Заказ выпадает из обоих отчётов** (строка 3 правила)
  Решение согласовано осознанно
  Смягчение: три уровня поиска перед алертом, алерт содержит всё для ручного решения,
  заказ назван поимённо и не исчезает молча
- **Полигон приближённый**
  Смягчение: буфер 1 км наружу, dry-run на боевых данных до включения,
  ошибка в сторону города безопаснее ошибки в сторону выпадения
- **Имена в Smartup расходятся с именами в адресной программе**
  Смягчение: поиск по координатам как второй уровень, dry-run покажет расхождения
    поимённо до включения
- **Задвоение отправки при повторе события**
  Смягчение: статус `ambiguous` блокирует автоповтор, как сейчас

# Детализация дня в календаре логистики, разбивка город и область

**Дата:** 2026-08-10
**Статус:** согласовано по макетам, ожидает реализации
**Макеты:** `calendar-day-detail-mockup.html`, `calendar-day-detail-mockup-v2.html` (сессионный scratchpad, в репозиторий не входят)

## Задача

Ячейка календаря логистики маленькая, в неё помещается только общая сумма
Пользователю нужна разбивка по зонам доставки и поимённый список заказов,
поэтому клик по дню должен раскрывать детализацию: сколько заказов и возвратов
ушло в город, сколько в область, и какие именно это заказы

## Что видит пользователь

### Не меняется

Ячейка календаря остаётся прежней: номер дня, `N зак.`, `N возв.`, `N блок.`,
бейдж выходного. Месячные метрики над сеткой прежние

### Меняется

1. Правая боковая панель `calendar-detail` убирается, сетка занимает всю ширину
2. Под сеткой раскрывается детализация выбранного дня:
   - шапка с датой, днём недели, бейджем рабочего дня, стрелками предыдущий и
     следующий день, кнопкой смены статуса дня
   - три карточки: **Город**, **Область**, **Итого за день**, в каждой заказы,
     возвраты, блоки, ниже число клиентов и разрез активные и завершённые
   - карточка «Итого» дополнительно показывает заказы вне логистики
3. Ниже список заказов с двумя вкладками, **Город** и **Область**
   - счётчики прямо на вкладке: `Город 96 + 7 возвр.`
   - под вкладками строка сводки активной зоны
   - фильтр `Все / Заказы / Возвраты` действует на активную вкладку
   - кнопка выгрузки XLSX действует на активную вкладку
4. Колонки списка: клиент (с адресом и представителем), товары (с файлом
   источником), блоки (скан из плана и прогресс), окно доставки, статус,
   номера SkladBot и Smartup, сумма
5. Возврат идёт строкой внутри своей зоны, отличается фоном и бейджем «Возврат»

### Управление нерабочим днём

Кнопки «Не работает» и «Работает» переезжают из боковой панели в шапку
детализации, поле причины остаётся, поведение и эндпоинт прежние

## Правила данных

### Зона считается на лету, а не хранится

Зона заказа нигде не сохраняется, её вычисляет `classify_order` из
`backend/app/logistics_zone_service.py` по трём правилам в этом порядке:

1. клиент найден в справочнике `logistics_region_points` по точному имени после
   нормализации, значит **область**
2. координат нет или они не парсятся, значит **город**
3. точка внутри `TASHKENT_CITY_POLYGON`, значит **город**, снаружи **область**

Календарь обязан звать ту же функцию, а не свою копию правил, иначе разбивка на
экране разойдётся с XLSX-отчётом логистики

### Возвраты

Сейчас `is_logistics_candidate_order` отсекает возвраты до классификации, и в
зоны они не попадают вообще. У возврата есть клиент и координаты, поэтому к нему
применяется тот же `classify_order`, и возврат учитывается в своей зоне

### Заказы вне логистики

`is_logistics_candidate_order` также отсекает самовывоз (`is_pickup_address`) и
заказы, заблокированные SkladBot по нехватке остатка
(`is_skladbot_stock_shortage_blocked_order`). Эти заказы не входят ни в город, ни
в область и не попадают в списки, но показываются числом в карточке «Итого»,
чтобы разрыв между цифрами был объяснён, а не выглядел потерей

### Пустой справочник областных точек

`build_logistics_reports` имеет страховку: при пустом справочнике вся доставка
считается городской и уходит одним файлом. Календарь повторяет это поведение и
показывает предупреждение над карточками, иначе экран разойдётся с отчётом

## API

### Существующий эндпоинт, расширяется

`GET /api/v1/admin/logistics-calendar?month=YYYY-MM`

К каждому дню добавляются поля:

| Поле | Тип | Смысл |
|------|-----|-------|
| `city_orders` | int | заказы города, без возвратов |
| `region_orders` | int | заказы области, без возвратов |
| `city_returns` | int | возвраты города |
| `region_returns` | int | возвраты области |
| `city_blocks` | int | плановые блоки города |
| `region_blocks` | int | плановые блоки области |
| `excluded_orders` | int | самовывоз и заблокированные по остатку |

К календарю целиком добавляется `region_directory_empty: bool`

Инварианты, проверяются тестами:

- `city_orders + region_orders == orders_count`
- `city_returns + region_returns == returned_orders`
- `city_blocks + region_blocks == planned_blocks`

### Новый эндпоинт

`GET /api/v1/admin/logistics-calendar/day/{service_date}/orders`

Ответ:

```json
{
  "date": "2026-08-07",
  "generated_at": "2026-08-10T07:41:00Z",
  "region_directory_empty": false,
  "orders": [
    {
      "order_id": "…",
      "zone": "city",
      "is_returned": false,
      "client": "…",
      "address": "…",
      "representative": "…",
      "products": "Marlboro Red; Parliament Aqua",
      "source_file": "zakaz_07_08.xlsx",
      "quantity_blocks": 24,
      "scanned_blocks": 24,
      "remaining_blocks": 0,
      "status": "completed",
      "delivery_from": "09:00",
      "delivery_to": "13:00",
      "skladbot_request_number": "…",
      "smartup_id": "…",
      "line_total": 42720000
    }
  ]
}
```

Плоский список с полем `zone`, вкладки фильтруют его на клиенте: два массива в
ответе дублировали бы схему без выгоды

Заказы вне логистики в `orders` не входят, их число берётся из месячного ответа

Права: чтение, как у месячного календаря, вкладка доступна по `client_points:read`
Запись остаётся только у `POST /admin/logistics-calendar/day`

### Выгрузка XLSX

Кнопка зовёт существующий `GET /api/v1/logistics/report?shipment_date=…&zone=…`
Файл, его имя и содержимое не меняются, меняется только место, откуда его дёргают
Сейчас веб-фронт этот эндпоинт не вызывает вообще, вызов новый

## Ограничения, которые надо знать до реализации

1. **Историческая разбивка приблизительная.** Зона считается текущим кодом и
   текущим справочником, а не теми, что действовали в тот день. Правило
   сопоставления менялось 08.08.2026 (PR #114), справочник пополнялся 09.08.2026
   Значит разбивка за прошедшие даты может отличаться от того, что реально ушло
   в XLSX в тот день. Это свойство подхода, а не дефект, и оно должно быть
   названо в интерфейсе одной строкой в шапке детализации
2. **Заказ без координат считается городским.** Это правило классификатора,
   в календаре оно даст тот же перекос, что и в отчёте
3. **Публичный репозиторий.** Имена контрагентов, координаты и содержимое
   адресной программы не попадают в тесты, фикстуры, логи и документы
   В тестах вымышленные имена вида `Тест Клиент 1`

## Границы работы

Входит: разбивка в месячном ответе, эндпоинт списка заказов дня, детализация в
веб-админке, вкладки, фильтры, выгрузка XLSX из детализации, стили, тесты

Не входит: изменение правил классификации, изменение XLSX-отчёта и его имени,
изменение Telegram-маршрутов и расписаний, хранение зоны в БД, пагинация списка
заказов дня (день это сотни строк, они грузятся одним ответом)

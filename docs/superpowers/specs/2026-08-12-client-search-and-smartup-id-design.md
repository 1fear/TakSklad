# Расширенный поиск клиентов и Smartup ID из шаблона отправки заказов

Дата: 2026-08-12
Статус: согласовано с Антоном в постановке задачи, реализация автономная

## Задача

1. На вкладке «Клиенты» панели управления искать по имени, адресу, координатам,
   SkladBot ID и Smartup ID в одном поле
2. Smartup ID должен подтягиваться из «Шаблона отправки заказов на склад»,
   где колонка «ИД заказа» и есть идентификатор сделки Smartup

## Что уже есть

`GET /api/v1/admin/client-points` отдаёт агрегат точек: сохранённые `client_points`
плюс точки, выведенные из заказов. Поиск существует в двух местах и покрывает
одно и то же:

| Место | Поля поиска |
|---|---|
| `client_points_service.list_client_points`, параметр `query` | client_name, point_name, address, representative, coordinates |
| `AdminWorkspace.filterClientPoints`, локально | те же плюс delivery_from, delivery_to |

Фронт грузит весь список один раз (лимит 2000, TTL-кеш) и фильтрует локально,
`query` в API не передаёт

Идентификаторы заказов живут не на точке, а на заказе:

| Идентификатор | Где лежит |
|---|---|
| Smartup ID | `orders.raw_payload.source_order_id` в форме `smartup:<число>`, плюс то же поле у позиций |
| Номер заявки SkladBot | `orders.raw_payload.skladbot_request_number`, формат `WH-R-*` или `WR-*` |
| ID заявки SkladBot | `orders.raw_payload.skladbot_request_id`, положительное число |
| Заявка возврата | `skladbot_return_request_number`, `skladbot_return_request_id` |

Excel-импорт кладёт в `source_order_id` синтетический хеш
`stable_hash({date, payment, client, address})`, поэтому у заказов из шаблона
Smartup ID сейчас пустой везде: в таблице заказов, в истории клиента,
в ежедневном XLSX-отчёте SkladBot

## Решение

### Часть 1: идентификаторы попадают в клиентскую точку

`list_client_points` получает ещё один CTE, который группирует идентификаторы
заказов по тому же `point_key`, что и остальные агрегаты. Из него берутся две вещи:

- `search_identifiers` в ответе API: канонизированный и дедуплицированный список
  идентификаторов точки через пробел
- расширение серверного `query`: сырой блок идентификаторов добавляется
  в поисковую строку, чтобы параметр API вёл себя так же, как локальный фильтр

Канонизация в Python поверх готовых контрактов `skladbot_contracts`:

| Токен | Правило | Что попадает в `search_identifiers` |
|---|---|---|
| `smartup:266627707` | `internal_smartup_id_from_source` | `266627707` |
| `WH-R-2026-0001` | `canonical_skladbot_request_number` | как есть |
| `1002` | `canonical_remote_request_id` | как есть |
| sha256-хеш Excel-импорта | не проходит ни одну проверку | отбрасывается |

Отбрасывание хешей обязательно: иначе на каждый заказ в ответ уезжает 64 символа
мусора, а поиск начинает ловить случайные совпадения

Координаты сравниваются в двух формах. Импорт хранит их как `41.296549, 69.277177`
с пробелом, а в шаблоне и в буфере обмена они выглядят как `41.296549,69.277177`.
Поэтому в поисковую строку добавляется вариант координат без пробелов,
а запрос сравнивается и как есть, и со снятыми пробелами. Это работает в обе стороны
и не требует угадывать формат

### Часть 2: Smartup ID из шаблона

`excel_importer` учится читать колонку «ИД заказа». Значение принимается,
только если это положительное целое (`[1-9][0-9]{0,39}`), у ячеек-чисел снимается
хвост `.0`. Всё остальное игнорируется молча, как и любая необязательная колонка

Живых парсеров Excel два, и оба шлют строки в один и тот же
`POST /api/v1/imports`, поэтому колонка читается в обоих:

| Канал | Парсер | Что добавлено |
|---|---|---|
| Telegram-бот | `backend/app/excel_importer.py` | алиас `smartup_order_id` и ключ строки «Smartup ИД заказа» |
| Десктопное приложение | `src/taksklad/excel_import.py`, алиасы в `src/taksklad/config.py` | то же, ключ ставится после `make_order_id`, чтобы сделка не вошла в хеш заказа |

Проверку и канонизацию делает один `normalize_smartup_order_id` в `imports_service`,
поэтому оба канала дают одинаковую личность заказа

Дальше идентификатор расходится по двум адресам:

| Куда | Значение | Зачем |
|---|---|---|
| `orders.raw_payload.source_order_id` | `smartup:<id>` вместо синтетического хеша | это поле читают все восемь мест, которые показывают Smartup ID |
| `order_items.raw_payload.smartup_order_id` | `<id>` | поиск находит клиента по любой сделке, даже если в одном заказе их несколько |

Ключевое ограничение: **`row["source_order_id"]` не меняется**. Он остаётся
синтетическим хешем и продолжает работать как ключ склейки позиций
(`position_merge_key`) и как публичный внешний идентификатор логистики
(`logistics_external_id`). Группировка заказов (`order_key`) тоже не трогается:
`smartup_deal_id` остаётся признаком только автоимпорта Smartup, поэтому
число заказов и число заявок SkladBot после изменения ровно то же, что до него

`logistics_external_id` отдельно проверен: он пропускает значения с префиксом
`smartup:` и падает на уровень позиции, где хеш сохранён. Вывод логистики
не меняется ни на символ

Для заказа, который уже существует (дозаказ, повторный импорт того же файла),
вызывается `preserve_order_smartup_identity`: она заполняет пустую личность
и никогда не перезаписывает заполненную

## Client-facing before/after

Изменение видимого вывода ровно одно и оно является целью задачи: там, где
Smartup ID у заказов из Telegram-шаблона был пустым, появляется реальный номер сделки

| Поверхность | Было | Стало |
|---|---|---|
| Вкладка «Заказы», колонка Smartup ID | пусто | `266627707` |
| История заказов клиента, строка `Smartup ID:` | `Smartup ID: —` | `Smartup ID: 266627707` |
| Ежедневный XLSX SkladBot, колонка `Smartup ID` на листах заявок и КИЗ | пусто | `266627707` |
| Поле поиска на вкладке «Клиенты», placeholder | `Поиск клиентов` | `Клиент, адрес, координаты, Smartup ID, SkladBot ID` |

Структура отчётов, названия колонок, имена файлов, маршрутизация Telegram
и типы сообщений не меняются. Новых сообщений и новых отправок нет

Заказы, импортированные до этого изменения, остаются без Smartup ID: в их
raw_payload его никогда не было и восстановить его неоткуда. Бэкфилл в объём
задачи не входит

## Что осознанно не делается

- Поиск не переезжает на сервер. Список точек уже загружен целиком, локальный
  фильтр даёт мгновенный отклик без запроса на каждое нажатие, а счётчики
  «Показано N из M» сохраняют смысл
- Позиции разных сделок Smartup внутри одного заказа не разделяются, хотя
  docstring `position_merge_key` намекает на такую семантику. Это отдельное
  изменение поведения склада и оно не запрашивалось
- Отдельные поля поиска по каждому идентификатору не вводятся: одно поле,
  которое ищет по всему, короче в использовании и не требует от оператора
  заранее знать, какой у него на руках идентификатор

## Риски и как они закрыты

| Риск | Закрытие |
|---|---|
| Колонка «ИД заказа» в чужом файле содержит не сделку Smartup | Алиас только кириллический «ИД заказа» плюс явные Smartup-имена, значение обязано быть положительным целым. Латинская «ID заказа» не берётся: так называется колонка в собственном экспорте заказов TakSklad |
| Ответ API распухает от идентификаторов | В `search_identifiers` попадают только канонические токены, sha256-хеши отброшены. На заказ приходится порядка 30 символов |
| Агрегат идентификаторов замедляет вкладку | Один проход по orders и order_items с группировкой, результат кешируется TTL-кешем панели на весь сеанс |
| Ломается склейка позиций или число заявок SkladBot | `row["source_order_id"]` и `order_key` не трогаются, тест фиксирует, что число заказов и позиций после импорта шаблона не изменилось |

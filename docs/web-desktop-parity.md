# Паритет web-панели и Windows-приложения

Дата: 2026-07-27.

Документ отвечает на один вопрос: **можно ли отказаться от Windows-приложения,
не потеряв функционал склада.** Ответ на 2026-07-27 — **нет**, и ниже перечислено,
что именно этому мешает.

План перехода: web-панель и Windows-приложение работают **параллельно** на одном
backend, склад постепенно переносит операции в браузер, приложение выключается
только после закрытия блокеров из раздела «Блокеры отказа от приложения».

## Метод

Проверялись 15 доменов десктопа (57 модулей, ~16 000 строк) против web-контура
(`frontend/`) и backend (`backend/app/`). Для каждой операторской возможности
искался эквивалент в коде, затем каждый заявленный пробел проверялся отдельно
с задачей его опровергнуть. Слой истины — код и тесты; live/operator/physical
не проверялись.

Классификация:

- `COVERED` — web делает то же самое;
- `PARTIAL` — web делает меньше, и оператор это заметит;
- `MISSING` — в web этого нет;
- `DESKTOP_ONLY` — имеет смысл только для локального Windows-клиента.

Эти домены **не** блокируют отказ от приложения — они давно живут на сервере:

| Домен | Состояние |

| SkladBot | Сопоставление заявок и возвраты выполняет `backend/app/skladbot_worker.py` (отдельный контейнер, интервал 60 с). `src/taksklad/skladbot.py` не импортируется ни одним модулем — legacy. |
| Excel-импорт | Десктопный вход уже мёртв: `src/taksklad/app_layout.py:97` выставляет `import_btn = None`, ни один виджет не вызывает `import_excel_orders`. Живые пути — Telegram-воркер и `/admin`. |

Вывод: примерно треть кодовой базы десктопа — уже не используемый код. При
выводе приложения из эксплуатации эти модули удаляются без потери функционала.

## Дефекты web-контура, найденные и исправленные в этой задаче

Это были не «недостающие фичи», а новые дефекты самой web-панели. Все три
исправлены и закрыты тестами, которые проверены на падение без исправления.

### 1. Склейка КИЗов на аппаратном сканере (P0, исправлено)

Десктоп при отклонении скана очищает поле ввода
(`src/taksklad/app_scanning.py:113`). Web намеренно оставляет код в поле и при
этом возвращает в него фокус, поэтому keyboard-wedge сканер **дописывал**
следующий код к отклонённому.

Проверено, что склеенный код проходил всю защиту насквозь:

```
0104006396053947217TEST01 + 0104006396053947217BUSY01 → 50 символов
формат-гард: проходит (префикс 01, длина в диапазоне, ASCII)
scan_product_mismatch: False даже для распознанного «Chapman Red OP»,
   потому что product key определяется по префиксу, а у склейки он валидный
итог: мусорный КИЗ записывался в scan_codes и kiz_movements как настоящий блок
```

Исправление: при отклонении поле выделяется целиком, следующий скан заменяет
содержимое. Код оператору по-прежнему виден.
Тест: `frontend/src/__tests__/WarehousePanel.test.tsx` — «выделяет отклонённый код…».

### 2. Потерянная проверка формата КИЗа (P0, исправлено)

`validate_kiz_code` существовала **только** в десктопе
(`src/taksklad/utils.py:96`); backend формат никогда не проверял. Проверено, что
backend принимает `"ПРИВЕТ"`, `"abc"`, `"01"` и строку из 300 символов для любой
позиции, чей товар не распознаётся каталогом Chapman.

Исправление: правило перенесено в браузер дословно, с теми же операторскими
сообщениями (`frontend/src/features/warehouse/kizFormat.ts`), включая разделитель
GS `\x1d`, который несут реальные DataMatrix-коды.
Тесты: `frontend/src/__tests__/kizFormat.test.ts` и `tests/test_kiz_format_contract.py`
(общий корпус на обеих сторонах, чтобы реализации не разошлись).

Серверное ужесточение в этот релиз **не** входит: backend никогда не проверял
формат, его правка изменила бы поведение живого API, которым пользуется и
работающее приложение. Вынесено в отдельный релиз.

### 3. Пустой лист при обычной печати из браузера (P1, исправлено)

`@media print { body * { visibility: hidden } }` не был ограничен модалкой, из-за
чего Ctrl+P на `/` печатал пустую страницу.
Исправление: правило ограничено `body.warehouse-print-open`.
Тест: `tests/test_frontend_print_contract.py`.

## Открытый дефект, решение за владельцем

### Молчаливое обрезание списка активных заказов (не исправлено)

`listActiveOrders` запрашивает `limit=500`, backend режет до **200**
(`normalize_page_limit(..., maximum=200)`), заголовок `next_cursor` не читается,
кнопки «загрузить ещё» нет.

- `frontend/src/api.ts:572`, `frontend/src/features/warehouse/WarehousePanel.tsx:104`
- `backend/app/orders_service.py` — `list_active_orders_page`

При более чем 200 активных заказах оператор молча не видит остальные. Десктоп
загружает весь список. Опасна именно молчаливость: признака обрезания в интерфейсе
нет.

Не исправлено намеренно: любое решение (постраничная догрузка по курсору либо
явное предупреждение в интерфейсе) — client-facing изменение, требующее
согласования по контракту `AGENTS.md`.

## Блокеры отказа от приложения

Пока не закрыты — приложение выключать нельзя.

### Офлайн-работа склада (P0)

Единственная и главная причина существования десктопа. При недоступном backend
приложение продолжает сканировать: durable-очередь `pending_backend_events`,
локальный backup КИЗов, идемпотентный повтор при восстановлении связи
(`src/taksklad/backend_events.py`, `src/taksklad/storage.py`).

В браузере офлайн-очереди нет и не планировалось: это зафиксированное проектное
решение. Следствие: **при обрыве связи с backend склад останавливается.**

Решение — за Антоном, вариантов два:
1. реализовать в web durable-очередь (service worker + IndexedDB) с той же
   идемпотентностью и audit-гарантиями;
2. принять остановку склада на время недоступности backend как бизнес-риск и
   держать приложение как аварийный контур.

Пока выбор не сделан, отказ от приложения невозможен.

### Печать как складская операция (P1)

Десктоп относится к печати как к части операции, web — как к просмотру:

- десктоп печатает сводный лист **до** фиксации завершения, web фиксирует, затем предлагает печать;
- десктоп держит durable-очередь ненапечатанных сводок и допечатывает при следующем запуске;
- десктоп умеет повторно напечатать лист по ранее завершённому заказу — в web снимок живёт только в памяти вкладки и теряется при перезагрузке;
- десктоп даёт выбор принтера и формат термоэтикетки с запоминанием параметров;
- десктоп обнаруживает сбой печати и показывает ошибку.

### Ориентация в работе (P1)

- поиск по списку заказов — на операторской поверхности его нет, список это выпадающий `<select>`; сам поиск реализован, но только на `/admin`, куда роль `operator` не имеет доступа;
- фото товара и GTIN текущей позиции;
- автопереход на первую незакрытую позицию и кнопка «следующая позиция»;
- счётчики смены и списка.

### Важный нюанс роли

Часть функций формально в web есть, но недоступна роли `operator`. Пример: поиск
по заказам реализован на сервере строгим надмножеством десктопных 6 полей
(`backend/app/admin_service.py:353-367`), но живёт на `/admin`, а роль `operator`
не имеет `admin:read` (`backend/app/access_policy.py:41-48`). Для оператора склада
такой функции нет. При выводе приложения такие пункты нужно либо переносить на
операторскую поверхность, либо расширять права.

## Риски параллельной работы web и приложения

Отдельная проверка: склад будет работать в браузере и в приложении **одновременно**
на одном backend. Четыре независимых агента искали, что при этом ломается.
Найдено 18 проблем, из них **14 ломают работающее приложение**.

Важно разделять: часть из них — **следствие этого кандидата**, часть существовала
раньше и просто становится достижимой чаще при двух клиентах.

### Внесено этим кандидатом — исправлено

Раньше такой скан подтверждался как `synced` и КИЗ терялся тихо; кандидат сделал
поведение fail-closed, но при этом заблокированное событие удалялось из очереди,
а его единственным следом оставался список в памяти, который интерфейс
выбрасывает, если позиция оператора не совпала. Исправлено:

| Severity | Проблема | Исправление |
|---|---|---|
| P1 | Очередь молча выбрасывала физически отсканированные КИЗы, если web успел закрыть позицию раньше | Заблокированные события пишутся в durable-секцию `blocked_backend_events` (та же SQLite-очередь, что и `pending_backend_events`), переживают перезапуск и попадают в счётчики диагностики |
| P1/P2 | Совет «сканируйте другой код» загонял оператора в бесконечный цикл: позиция закрыта на сервере, любой код получит тот же 409 | Отдельная ветка сообщения: «Позиция уже закрыта на сервере. Нажмите «Обновить»» — единственный рабочий выход |

Тесты (проверены на падение без фикса):
`tests/test_backend_bridge.py` — сохранение при закрытой позиции и идемпотентность
повторных синхронизаций; `tests/test_desktop_ui_contract.py` — текст сообщения;
`tests/test_storage_concurrency.py` — round-trip через реальный SQLite и счётчики.

Остаётся открытым: заблокированные события **сохранены**, но всё ещё не
показываются оператору, если относятся не к текущей позиции. Это P2 и требует
изменения интерфейса десктопа — вынесено из этого релиза.

Обе правки меняют поведение production-десктопа `2.0.54` и требуют согласования
по client-facing контракту `AGENTS.md` до выката. Порядок выката: сначала новая
сборка десктопа, затем backend.

### Существовало ранее, обостряется при двух клиентах

| Severity | Проблема |
|---|---|
| P0 | complete_order validates KIZ completeness on a snapshot but locks only the orders row — concurrent undo archives an order with a missing KIZ (`backend/app/orders_service.py:538`) |
| P0 | delete_active_order races a concurrent scan and leaves an orphaned outbound kiz_movement that permanently bricks the KIZ (`backend/app/order_actions_service.py:71`) |
| P1 | delete_active_order can destroy a concurrently created scan with no KIZ movement, permanently bricking the code (`backend/app/order_actions_service.py`) |
| P1 | create_scan has no order-status guard, so KIZs are recorded onto orders the web admin already cancelled/archived (`backend/app/orders_service.py:245`) |
| P1 | Desktop queue permanently discards order_complete events rejected as 'incomplete', and that class of blocked event can never be surfaced to the operator (`src/taksklad/backend_events.py:305`) |
| P1 | reset_order_for_rescan releases codes with no fencing, so a stale desktop queue silently re-completes the item with the codes that were just reset (`backend/app/order_actions_service.py:231`) |

Общий корень у P0-гонок один: `complete_order` и `delete_active_order` блокируют
строку `orders`, а `create_scan`/`undo_scan` — строку `order_items`. Клиенты
берут **разные** блокировки и не видят друг друга. Кандидат исправил это только
для `reset_order_for_rescan`; соседние пути остались как были.

### Что это значит для плана перехода

Параллельная работа возможна, но до выката нужно закрыть как минимум два P1,
внесённых этим кандидатом, иначе десктопный оператор получит зависшую позицию
и потерянные сканы. P0-гонки существовали и до кандидата, но при двух клиентах
их вероятность заметно выше — их стоит закрыть в этом же релизном цикле.

## Условия выключения приложения

Выключать Windows-приложение можно только когда одновременно выполнено:

1. закрыт вопрос офлайн-работы (реализация в web либо принятый бизнес-риск);
2. закрыты P1-блокеры печати и ориентации из разделов выше;
3. web-контур прошёл физическую операторскую приёмку с реальным сканером и
   принтером — [приёмка веб-склада](web-warehouse-acceptance.md), раздел B;
4. склад отработал согласованный период параллельно на web и приложении без
   расхождений в КИЗах и остатках;
5. `version.json` не поднимает `min_supported_version` выше версии, на которой
   склад реально работает, до самого выключения.
